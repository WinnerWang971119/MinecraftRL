# M4 Self-Play (issues #8, #9, #10) + iron loadout (#33) Plan

**Goal:** Drive the second bot in every arena with a frozen past-self policy, sampled by PFSP from a persisted snapshot pool, with Elo logged over training — so a self-play-trained, iron-equipped agent can fight human challengers on 2026-08-21.

**Approach:** Reuse the `opp_action` wire seam that already exists. `MCPvPEnv` gains a second `PerceptionFilter` and computes BOTH seats' observations **eagerly, exactly once per ingested state**, caching them; `opponent_observation()` returns the cache. A `SnapshotOpponentDriver` — built by the same lock-guarded memoized per-arena factory pattern as `build_scripted_opponents` — feeds that mirrored observation to a frozen `DuelingDRQN` and returns its greedy macro. Both fighters get an iron sword and full iron armor, which is a **regime migration**, not a cosmetic change.

> **Line anchors in this document are APPROXIMATE.** They were taken across two branches and drift 4-7 lines. Grep for the named symbol; never trust an offset.

Approach chosen at Phase 4. Both independent consultants ENDORSED it and converged separately on the same refinement: compute eagerly and cache, never lazily inside the accessor.

## Decisions

- **Worktree at `/Users/diego/Documents/MinecraftRL-m4`, branch `feat/m4-selfplay`** off `fix/yaw-convention` — the live run has `bridge_restart=on`, so checking the main tree to another branch would have auto-restarted bridges silently running different code mid-run.
- **Run name is `m4_selfplay`.** The live bare-handed M3 retry owns `runs/m4.pt` / `runs/m4.best.pt`, which is also this run's warm-start source.
- **Mirrored observation is computed eagerly and cached.** Non-negotiable: a lazy accessor ages perception memory a variable number of times per window.
- **Mirror logic lives in a sibling module** so the frozen env file's diff stays reviewable.
- **The opponent gets an iron sword, not just armor.** The datapack never arms it and `dummyResetTemplate` is `[]`. Armor without a weapon = ~0.4 HP per punch, ~50 hits to kill, nothing terminating in 600 steps — every episode a draw, PFSP flat, Elo pinned, window wasted.
- **Opponent `velocity` is read from the OPPONENT'S OWN connection (T20).** Found during T5's review: three handlers write a non-self `entity.velocity` (`entity_velocity`, `sync_entity_position`, `spawn_entity_living`) but only `entity_velocity` can fire on pinned 1.21.1 — the other two are 1.21.3 and pre-1.19 respectively, and it fires on knockback/explosions, not per tick; `rel_entity_move` and `entity_move_look` translate position only, and `sync_entity_position` is the 1.21.3 packet, dead on pinned 1.21.1. So `opp_vel_local` (obs **16-18** — verified `FIELD_SLICES['opp_vel_local'] == slice(16, 19)`; 14-15 are `opp_facing_sin/cos`, an earlier revision of this plan said 14-16 and was wrong — 3 of 23 features) has carried a stale knockback impulse or zero for the life of the project — the agent has never perceived opponent motion. Same defect class as `damage_dealt`. Fixing it is safe precisely because the channel was noise: the net learned to ignore those inputs, so adding real signal cannot break what was never used.
- **`on_ground` is read from the OPPONENT'S OWN connection** (`this._opponentBot().entity.onGround`), never `entity.onGround` seen through the learner's client. This is the exact failure that killed `damage_dealt` for the life of the project: mineflayer does not reliably populate other-entity state. For a human challenger, who has no bot connection, fall back to the handle view and record the degradation.
- **Elo is TWO series, resolving the eligibility contradiction:**
  - `elo/learner_online` — updated from every training match, with BOTH epsilons recorded on the match record. Dense and noisy. Feeds PFSP only.
  - `elo/learner_rated` — updated only from eval-cycle matches where learner AND opponent are at ε=0. Sparse and clean. **This is the AC7 rising-trend series and the checkpoint-selection input.**
  A single "online Elo, greedy-only" rule was self-contradictory: the learner anneals to ε=0.05 and opponents sit at ε=0.02, so no training match would ever have qualified and the curve would have been empty.
- **Learner's initial Elo is 1000.** Snapshot ratings are frozen at creation to the learner's rating then.
- **Pool bootstrap:** snapshot 0 IS sampleable until a second distinct version exists. The same-version exclusion applies only once the pool holds ≥2 distinct versions — otherwise the first episodes have no legal opponent.
- **Pinned references are created on a schedule, not assumed:** snapshot 0 at seed, then promotion at grad steps 5,000 and 15,000. `pinned_references()` returns however many exist; the eval degrades gracefully to 1 or 2.
- **No eviction in this run.** ~30-45 snapshots × 2.4 MB is ~110 MB.
- **Snapshot nets live on CPU** — 25 private frozen clones must not contend with the learner.
- **Armor cannot be verified by the reset gate.** `items()` covers slots 9-44 (`prismarine-windows/index.js:11`); armor is 5-8. Verification is a server-authoritative `data get entity` read, and it is **fail-closed**.
- **The demo checkpoint is selected from ONE immutable on-disk candidate**, evaluated against all references in a single frozen state — never `trainer.online` by reference.
- **Frozen opponents act at ε=0.02** in training so greedy-vs-greedy pairs cannot lock into deterministic loops. Draws score 0.5.
- **The algo-task contract is honoured** by keeping one scripted-benchmark eval track, so the self-play net has an absolute yardstick comparable to M3.

## Data Model

```python
@dataclass(frozen=True)
class SnapshotRecord:
    snapshot_id: int          # immutable policy-version identity
    grad_step: int
    path: str                 # runs/<run>/snapshots/snap_<id>.pt
    elo: float                # frozen at creation
    pinned: bool

@dataclass(frozen=True)
class MatchResult:            # the contract T12 rates from
    snapshot_id: int
    learner_epsilon: float
    opponent_epsilon: float
    score: float              # 1.0 win / 0.5 draw / 0.0 loss
    rated_eligible: bool      # True iff BOTH epsilons == 0.0

@dataclass
class MatchStats:
    plays: int
    learner_wins: float
    def win_rate(self) -> float: ...   # Beta(1,1) prior: (wins+1)/(plays+2)
```

Elo: `E_a = 1/(1+10**((R_b-R_a)/400))`; `R_a += K*(S_a-E_a)`, `K=24`, learner starts at 1000. Only the learner's rating moves.

PFSP weight for snapshot `i`: `w_i = f(p_i) + floor`, `f(p)=p(1-p)`, `floor=0.05/N`, then normalized. The Beta(1,1) prior makes `p_i` well-defined at zero plays, so `f` can never divide by zero or yield NaN.

Snapshot payload: `{"model", "grad_step", "code_version", "snapshot_id", "elo"}`.

### Pool (owner: T8; consumers: T9, T10, T12, T13, T18)

```python
class SnapshotPool:
    def add(self, state_dict, grad_step: int, elo: float, pinned: bool = False) -> SnapshotRecord
    def sample(self, rng, exclude_id: Optional[int] = None) -> SnapshotRecord
    def record_result(self, result: MatchResult) -> None
    def pfsp_weights(self) -> Dict[int, float]
    def pinned_references(self) -> List[SnapshotRecord]   # 1..3, however many exist
    def persist(self, payload: Mapping[str, Any]) -> None   # takes the payload so it never needs _lock (T9 hardening)
    @classmethod
    def load(cls, directory: str, *, sampling: str, log=None) -> "SnapshotPool"   # sampling REQUIRED (T9): a default silently resumes a uniform arm as pfsp
```
One lock guards registry/stats/Elo. Net loading happens OUTSIDE the lock. A missing/corrupt **unpinned** snapshot is dropped and resampled; a missing/corrupt **pinned** snapshot is FATAL.

## Error Handling

- **Unpinned snapshot missing/corrupt at sample time:** log loudly, drop from pool, resample. Never fall back to an untrained net.
- **Pinned snapshot missing/corrupt:** FATAL. Refuse to continue.
- **Pool empty / no legal opponent:** impossible — snapshot 0 stays sampleable until a distinct version exists.
- **Mirror requested but wire fields absent:** refuse at env construction, naming all five surfaces. Never substitute constants.
- **`opponent_observation()` before any state, or with the mirror off:** raise, matching `raw_opponent_view()`.
- **Episode aborted mid-flight (`BridgeError`):** not scored into Elo or PFSP, matching the scripted curriculum.
- **Armor/sword read-back fails:** abort launch, or abort that reset during an exhibition. Never proceed unarmored.
- **`--opponent selfplay` without `--warm-start`, or checksum mismatch:** config-level `ValueError` at startup.
- **`step()` reply loss:** unchanged — abort, never retry. `reset()` keeps its bounded reconnect.

## T17 — the learning canary, as built (`scripts/canary_selfplay.sh`)

**The choice: lower `--min-replay`, do not run longer.** The plan allowed either.
At the measured 4.8782 transitions/s/arena and the production `min_replay =
25_000`, warm-up alone costs 25000/(4 × 4.8782) = **21.4 minutes at 4 pads**
(42.7 at 2), and `Trainer.learn()` is a no-op for every second of it. The canary
runs `--min-replay 2000`, so it is warm in ~103 s at 4 pads and its 1,200-step
budget lands inside a ~30-minute window, so a second attempt after a fix costs
half an hour rather than three quarters of one. **A second attempt is not free
of state** — see *Every attempt starts clean* below. `min_replay` decides only WHEN
learning starts, never WHETHER the snapshot/PFSP/Elo/eval wiring works, and
wiring is all a canary can test. **Both numbers are printed in the verdict banner
and recorded in `evidence.json`** so this run's replay regime can never be
mistaken for the long run's.

**It starts nothing.** Boot order for anything live is Paper → bridges → driver;
the operator owns the first two. The canary verifies the fleet (Paper by TCP
connect, which is safe — Paper is multi-client; bridges by `lsof -nP -iTCP:<port>
-sTCP:LISTEN`, which opens no connection) and refuses with instructions if it is
not up. It also refuses to probe a port that already shows an ESTABLISHED peer:
`BridgeServer` accepts exactly ONE client and destroys the incumbent on a second
connection.

**Run it:**

```

DUMMY_KNOCKBACK_IMMUNE=false caffeinate -dimsu \
  server/setup/start-pads.sh --pads 25                             # operator
scripts/canary_selfplay.sh --warm-start /Users/diego/Documents/MinecraftRL/runs/m4.best.pt \
  --expect-sha256 1d3d0c600e2ad76e49f2a6be10859f492ae2877c40f186b14f8924102774d5b2 \
  --arenas 25
```

**`--arenas 25`, not 4, and the fleet booted at 25 to match.** Two independent
reasons. `OPPONENT_FROZEN` is the only proof `DUMMY_KNOCKBACK_IMMUNE=false`
reached the bridges and it covers ONLY the pads the canary ran on, so a 4-pad
canary certifies 4 of the 25 pads the night will use (and T19 refuses the launch
outright when a bridge listener is newer than the canary's measurement, so the
fleet cannot be re-booted wider afterwards). And more arenas fill `min_replay`
sooner, which is the entire point of a canary that has to take gradient steps.

**The two environment facts around it.** This worktree has no `.venv`, and all
three scripts default `PYTHON_BIN` to `${REPO_ROOT}/.venv/bin/python`, so without
the export every step dies at its interpreter preflight. And `pmset` reports
`sleep 1` on AC with nothing in the repo holding it off, so the assertion goes on
the fleet supervisor, the one process that lives for the whole window. See
RUNBOOK.md, *The self-play night*, for both in full.

**`--expect-sha256` is opt-in and verifies against the RECORD.** Omitted, the
digest is verified against nothing (the script warns and continues); given, the
preflight refuses with `WARM_START_DIGEST_MISMATCH` and exit 2 before any
connection. `runs/m4.pt` hashes to
`c4afabf60ec7b88135c6339817999d449da1725b0c5e195da93eff3c123ac369` and sits one
tab-completion away.

Exit 0 = GREEN (launch cleared), 1 = REFUSED, 2 = preflight/usage error raised
before the budget is spent (nothing ran), 3 = the run happened but could not be
JUDGED (the evidence collector raised). 3 exists because 2 promises "nothing was
run" and a collector failure breaks that promise after half an hour of fleet
time; treat it exactly as a refusal. `--analyze-only <dir>` re-runs the verdict
over an existing evidence directory, connects to nothing, and is handled before
every preflight check so it needs neither a fleet nor `--warm-start`.

**Phases:** preflight → fail-fast pre-probe (1 armored episode on the warm-start
net; a mis-geared or frozen fleet costs one episode, not the budget) → the short
run that actually learns → post-run probe on the FINAL checkpoint (strict) →
evidence + verdict.

**The refusal codes** (each prints WHY and what to check; each has a test in
`tests/test_canary_selfplay.py` proving it blocks):

`DRIVER_FAILED` · `ZERO_GRAD_STEPS` · `POOL_UNREADABLE` · `NO_NEW_SNAPSHOT` ·
`SNAPSHOT_UNCHANGED` · `STALE_POOL` · `PFSP_INVALID` · `RATED_ELO_EMPTY` ·
`DRAW_MAJORITY_TRAINING` · `DRAW_MAJORITY_PROBE` · `CHECKPOINT_UNLOADABLE` ·
`PROBE_FAILED` · `MISSING_ARMOR` · `NO_DAMAGE_DEALT` · `NO_DAMAGE_TAKEN` ·
`ACTION_COLLAPSE_LEARNER` · `ACTION_COLLAPSE_OPPONENT` · `COOLDOWN_METER_STUCK` ·
`COOLDOWN_DISAGREEMENT` · `OPPONENT_FROZEN`

That is 20 codes for the plan's 11 conditions. The extras are not padding:

- `DRAW_MAJORITY`, `ACTION_COLLAPSE` and the cooldown condition each split in
  two, because the two halves have different evidence and different fixes
  (training matches vs probe episodes; learner seat vs opponent seat; a meter
  that is pinned vs two meters that disagree) and one shared code would hide
  which half fired.
- `DRIVER_FAILED`, `POOL_UNREADABLE` and `PROBE_FAILED` are the fail-closed
  guards: when the evidence a condition needs was never produced, the gate
  refuses rather than reading absence as health.
- `STALE_POOL` is the one condition the plan did not anticipate, and it exists
  because the gate's own evidence is reusable: see *Every attempt starts clean*
  above. `SNAPSHOT_UNCHANGED` also diffs the newest snapshot against the
  **second-newest**, not only against snapshot 0 — a pool whose snapshots 1..N
  are clones of each other but differ from the seed is the same "one policy
  under many ids" failure, one archive cycle later.
- `OPPONENT_FROZEN` is the empirical check for `DUMMY_KNOCKBACK_IMMUNE=false`.
  macOS exposes no other process's environment (`ps -E` / `ps eww` show
  nothing) and `start-pads.sh` passes the setting via the env var rather than
  argv, so the flag cannot be read back — only its effect can. It refuses only
  when BOTH the reported speed AND the walked path are dead, so the unreliable
  velocity channel alone cannot false-refuse.

**`--best-checkpoint` is passed alongside `--checkpoint`, never alone.**

**Two traps this gate deliberately does NOT fall into:**

1. **The driver's exit code is not a health signal.** `_main_multi_arena` returns
   `0 if passed_m2 else 1`, and `passed_m2` is the M2 gate against the STATIONARY
   dummy — a self-play run never clears it, so a healthy canary exits 1. The
   verdict reads the `[multi done]` teardown line instead, and a test pins that
   exit codes 0/1/2/130 alone do not refuse.
2. **Only FULLY-CHARGED swings carry the loadout signature.** The charge scalar
   `0.2 + f²·0.8` multiplies the **raw** weapon damage *before*
   `getDamageAfterArmorAbsorb` runs, and absorption is not linear in the
   incoming damage — so it can never be applied over the post-armor 3.12. A
   90%-charged iron hit through full iron lands
   `damage_after_absorb(6.0 × 0.848, 15, 0) = 5.088 × (1 − 12.456/25) = 2.553`,
   not the `3.12 × 0.848 = 2.646` a flat percentage predicts. Either figure
   reads as "not 3.12" and would refuse a perfectly geared fleet, so the armor
   evidence is gated on the attacking seat's cooldown reading 1.0 at the
   decision. (`eval/combat_probe.py` pins the whole ladder: one gate tick short
   is `f = 0.92`, which lands 2.6590 — 85% of a cooled hit, from a scalar of
   0.877 on raw damage.)

### Every attempt starts clean

`build_snapshot_opponents` **load-extends** a pool it finds
(`if os.path.isfile(os.path.join(directory, INDEX_FILENAME)): pool =
SnapshotPool.load(...)`), and `SnapshotPool.load` restores the registry, both
Elo series **and** the match counters. A second attempt into the same
`--run-name` therefore inherits the first one's artifacts, and four refusals are
pre-satisfied by them even when the fix under test broke the wiring being gated:
`NO_NEW_SNAPSHOT` (the pool is already ≥ 2), `SNAPSHOT_UNCHANGED` (the newest
already differs from snapshot 0), `RATED_ELO_EMPTY` (`rated_matches` is already
nonzero) and `DRAW_MAJORITY_TRAINING` (this attempt's draws diluted by attempt
1's matches). `runs/<run>.pt` likewise lets `CHECKPOINT_UNLOADABLE` pass on a
stale file. Only `ZERO_GRAD_STEPS`, `DRIVER_FAILED` and the probe checks are
immune, because they read this attempt's truncated `driver.log` and this
attempt's live episodes.

The first run — the one that gates the 24-hour launch — was always sound. A gate
that stops gating on the *second* attempt is the manufactured confidence this
file exists to prevent, so it is closed twice:

1. **The preflight refuses to start** when `runs/<run>/snapshots/pool.json`,
   `runs/<run>.pt`, `runs/<run>.best.pt` or `runs/<run>/metrics.jsonl` already
   exists, naming each file and offering both ways out (delete them, or pass a
   fresh `--run-name`). Blocking, not a warning.
2. **`STALE_POOL`** is the verdict-level half, so it cannot be sidestepped by
   choosing a new name or by editing the preflight out. It refuses unless the
   newest snapshot is *proven* to be this run's: its file must have been written
   at or after the driver started, the pool's per-snapshot grad steps must read
   as one run's history rather than two concatenated, and the newest snapshot
   must not carry a grad step this run never reached.

### The gate chain, and why `DUMMY_KNOCKBACK_IMMUNE=false` is enforceable at all

`DUMMY_KNOCKBACK_IMMUNE` cannot be read back from a running process: macOS
exposes no other process's environment, and `start-pads.sh` passes it as an env
var rather than argv (`distributed.launcher.plan()` is called without the
kwarg, so no bridge argv carries the flag). The only proof is empirical, and it
is T17's `OPPONENT_FROZEN` check — which covers **only the processes it
probed**. So the launch gate:

1. requires the canary's measurement file, and re-reads T17's verdict through
   `canary_selfplay.sh --analyze-only` (which connects to nothing) — refusing
   unless it exits 0;
2. refuses if **any bridge listener started after that measurement was
   written**, parsed from `ps -o etime=` (macOS has no `etimes` keyword).

That makes the recommended order **one 25-pad fleet, booted once**: canary at
`--arenas 25`, then the smoke, then the launch. A 4-pad canary followed by a
25-pad smoke means a fleet reboot in between, and the knockback proof does not
survive it.

`SMOKE_POOL_NOT_GROWING`

Two of the five required quantities have no direct instrument, and the script
says so rather than inventing one:

- **transitions/s is DERIVED** (`episodes/s x the canary's armored episode
  length`). The multi-arena path logs no replay size and no queue length, so a
  transitions counter is not observable from outside the driver process, and
  adding one means editing `agent/train.py` — which T19 does not own. Both the
  derivation and the episode length it used are recorded in
  `smoke_measurements.json`.
- **queue depth is proxied by `episodes_received / grad_steps`**. The learner
  takes exactly one gradient step per drain pass and pulls at most
  `distributed.learner._DEFAULT_DRAIN_BATCH == 16` episodes per pass, so a ratio
  approaching 16 means every pass is hitting the cap. `collector_queue_max`
  defaults to 0 — the queue is UNBOUNDED, so there is no backpressure and the
  backlog shows up as RSS. A tripped `LearnerWatchdog` refuses under the same
  code.

RSS is sampled every 15 s for the driver and the JVM and projected forward with
a least-squares slope, but **only until the replay buffer is full** — past
capacity it stops growing, and extrapolating a straight line to 12 hours would
refuse every healthy run. The ceiling is a fraction of `hw.memsize`, not an
absolute.

Snapshot-load latency is timed by replaying exactly what
`SnapshotOpponentDriver.begin_episode` does — `pool.load_state_dict(record)`
then `net.load_state_dict(...)` — and judged as a share of ONE arena's mean
episode wall time, because it runs on the collector's own thread.

### PART 2 — the sizing, shown

```
measured armored episode length  ->  episodes/hour at 25 pads
  ->  episodes in the window  ->  the decay window (15% of them)
```

The length comes from the canary's **probe** figure (learner ε=0.05 / opponent
ε=0.02 — the run's terminal epsilons, which is where a run whose decay spans 15%
of its episodes spends the other 85%), never from the scripted-eval figure and
never from a constant. It is cross-checked against the length implied by the
canary's own collection rate (`4.8782 x 3600 / episodes-per-arena-hour`) and
refuses on a disagreement beyond 2x.

Two independent calibrations are pinned by the tests, and both reproduce
measurements the model was not fitted to: 100 serial eval episodes at 285 steps
comes out at **97 minutes** (measured), and 95-step episodes at 25 pads come out
at **~4,640 episodes/hour** (the M3 retry's measured rate).

The historical trap is a refusal: `EPS_DECAY_ABSURD` refuses a window outside
5-40% of the projected run, in **both** directions — the 142% failure and the
single-arena-number failure are the same bug seen from either side.

**Expect the driver's own startup line to disagree.**
`agent.train.epsilon_schedule_report` divides by
`train_config.projected_episodes(25)`, which is still built from the 285-step
bare-handed constant, so it will report roughly twice the true fraction. The
plan report prints what that line will say, and says to ignore it.

### PART 3 — the launch

`--eval-episodes` and `--reference-eval-episodes` are **derived**, not fixed at
this document's earlier `--eval-episodes 10`: the gauntlet is sized first and
keeps T13's per-reference default of 10, and the scripted yardstick takes
whatever time budget is left, targeting the middle of the 30-45 min band. With
an expensive armored eval the yardstick shrinks and the gauntlet holds, because
the gauntlet is the checkpoint-SELECTION input. `--eval-every-grad-steps` is
then derived so the designated arena spends at most half the night in eval.

The eval-cycle cost is sized from `armored_mean_episode_length_eval_vs_scripted`
— the periodic eval's own length — and the report prints `eval_opponent`
alongside it, so the regime travels with the number. When the canary's cycle
produced no such length, the sizing falls back to the **probe's** armored length
and says so; there is no greedy figure to fall back to, and never a constant.

Refusals: `CANARY_MEASUREMENTS_MISSING` · `CANARY_MEASUREMENTS_STALE` ·
`CANARY_NOT_GREEN` · `EPISODE_LENGTH_UNMEASURED` · `EPISODE_LENGTH_IMPLAUSIBLE`
· `EPISODE_LENGTH_DISAGREEMENT` · `EPS_DECAY_ABSURD` · `SMOKE_NOT_CLEARED` ·
`FLEET_NOT_READY` · `WARM_START_UNUSABLE` · `RUN_NAME_COLLISION` ·
`CHECKPOINT_UNSAFE` · `EVAL_CYCLE_TOO_LONG` · `EVAL_CADENCE_TOO_TIGHT` ·
`BUDGET_ENDS_EARLY` · `OPPONENT_NOT_SELFPLAY`

`BUDGET_ENDS_EARLY` names the flag it is catching: `--max-episodes` defaults to
10,000, which at 25 armored pads is a couple of hours, and the run then stops
with `stop_reason=max_episodes` and idles until morning. `CHECKPOINT_UNSAFE`
refuses `--best-checkpoint` without `--checkpoint` — the combination that
disables the periodic save AND makes the final save a no-op.

The argv is built by the gate, written to `launch_argv.txt` **only on a clear
verdict**, and read back by the shell, so the command that runs is the command
that was checked. Tests parse it through `agent.train._build_parser` and build a
`TrainConfig` from it, so a typo'd flag or a value the dataclass rejects fails
here rather than in the first second of the night.

### Watching the night: `scripts/watch_selfplay.sh`

Not one of T19's four parts and not a gate: a strictly read-only checker the
operator runs against the live run. It writes nothing, signals nothing, starts
nothing and opens no socket at all, `lsof` and `ps` only. It never connects to a
bridge port, because a second connection destroys the incumbent client.

Five badged signals (LIVENESS, GRAD STEP, FLEET, THROUGHPUT, EVAL) with OK /
WARN / ALARM / UNKNOWN verdicts; exit 0 on OK-or-WARN, 1 on ALARM, 2 on usage,
3 on UNKNOWN. Every path derives from `--run-name`, and the judgement is
stdlib-only, so it runs without the venv.

It exists for one failure the review accepted rather than patched: a collector
raising anything other than `BridgeError` dies inside the driver, `ActorPool`
does not abort, and the bridge process and its socket stay standing. **A
listening bridge is therefore not proof its collector thread is alive**, and the
line that reports it is the cross-signal note `FULL FLEET + COLLAPSED RATE`.
UNKNOWN is never OK: it means the signal could not be determined, and it names
the missing file. Full operator detail is in RUNBOOK.md, *The self-play night*.
